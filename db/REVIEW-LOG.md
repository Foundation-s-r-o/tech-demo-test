### Findings

1. **[resolve before 3b] Bitemporal semantics deviation.** The service uses
   *supersede-all-current-rows-then-insert* (details, addresses per type,
   religion) instead of the design's model where multiple current-belief rows
   with disjoint valid ranges coexist and overlaps are *rejected*. Effects:
   `BitemporalGuard` (Stage 2) is now dead code in main; superseded rows keep
   `VALID_TO = null`, so valid-time history ("what name was valid in 2010
   under current belief") is not representable — only transaction-time
   history survives; inserting a purely historical row (validTo in the past)
   destroys the person's current detail. This contradicts DESIGN.md §
   bitemporal satellites and the plan's own Stage 3 IT list (T3 overlap
   rejection, T4 point-in-time address query). Either (a) rework writes to
   the design semantics (BitemporalGuard + close-old-validity supersede
   pattern), or (b) explicitly adopt the simplified single-current-version
   model: delete the guard, amend DESIGN.md + ADR-0011, and reinterpret
   T3/T4 in the plan. Decide **before** 3b copies the pattern.
2. **Search is not access-logged.** `GET /api/persons` accepts
   `X-Access-Purpose` but ignores it — no `ACCESS_LOG` rows for search hits,
   though results carry names/DOB/sex/uid. Design rule is "every
   personal-data read is logged". Log one entry per returned person (or a
   search-scoped entry).
3. **Merge resolution not wired into reads** — `resolvePersonUid` is unused;
   `GET /{uid}` on a merged duplicate serves the duplicate record, and search
   doesn't exclude anonymized or merged persons. Fine while no merge endpoint
   exists; wire it when 3b/3c expose merges.
4. **Audit rows store minimal JSON** (`{"personUid": …}`/`{"detailId": …}`)
   vs the design's full old/new row images. Tamper-evidence is intact but
   forensic value is reduced — document as a deviation (ADR-0011/0012) or
   serialize the full DTO.
5. **Plan-scope slippage: `/me` + `/me/access-log` missing** (plan lists them
   in 3a). Citizen seeds don't exist yet either. Carry to 3c together with
   the CITIZEN seed account.
6. **Minor**: missing consent fields on consent-based religion returns 409
   (`ConflictException`) — semantically a 400 validation error; consider
   `@AssertTrue`-style DTO validation. `FlywayMigrationIT` doesn't assert the
   demo `PERSON` table is gone post-V8 (one-line test). Stage 2 findings #3
   (security-event listener) and #4 (`verifyChain` vs `CHAIN_HEAD`) remain open.
7. **Transitional breakage (expected, flag loudly):** the SPA still calls the
   deleted demo API — the UI is functionally broken against this backend, and
   `ui/api-docs.json` now drifts (doctor drift step + `test_openapi` + full
   E2E would fail) until Stage 5. The plan accepts this window; consider
   pulling the person-list/create UI slice of Stage 5 forward to shorten it.

### Gate results (run by reviewer)

`cd api && ./mvnw clean verify` — **BUILD SUCCESS** (all unit + 36 IT tests,
Checkstyle, JaCoCo floor met). UI untouched.

### Verified correct

- **T8 office scoping**: `assertOfficeAllowed` restricts CLERK to their own
  office on register, read, dissolution, and medical; SUPERVISOR + DPO are
  nationwide. Tested with real principals (mock users would have bypassed the
  office lookup — the IT correctly uses `@WithUserDetails`).
- **Registry-number uniqueness among current versions** enforced on register
  (portable replacement of the PG partial unique index), 409 on duplicate —
  IT-covered.
- **Amendments**: supervisor-only (`@PreAuthorize`), mandatory reason,
  supersede-then-insert with `SUPERSEDES_ID` + `APPROVED_BY` — matches the
  design's transaction-time versioning for vital records (this pattern is
  *correct* here, unlike the person satellites — see Stage 3a finding #1,
  which remains open for person data only).
- **Art. 9 medical data** isolated behind its own endpoints; reads
  access-logged with purpose; registrations access-log the record subject;
  writes append to the audit chain.

### Findings

1. **[fix in 3c] Amending an already-superseded version is not rejected.**
   `amend*` loads any version by id; if it is already superseded, its original
   `SUPERSEDED_AT` gets silently overwritten (history falsification) and a
   second amendment branch is created — two current records with the same
   registry number. Reject with 409 when `previous.supersededAt != null`.
2. **[fix in 3c] Amend path skips the registry-number uniqueness check.** An
   amendment may change office/bookYear/entryNo onto a value already used by
   another current record; PG's partial unique index would reject this, the
   app check runs only on register. Run the same check in amend (excluding
   the amended record's chain).
3. Registration's check-then-insert on the registry number has no
   serialization (same class as the Stage 2 merge-race note) — low risk
   single-instance; document with the others in ADR-0012.
4. DB CHECK violations (e.g. death record with no date/found/court basis)
   surface as **500** — add a `DataIntegrityViolationException` →
   400 problem+json mapping in `ApiExceptionHandler`.
5. GDPR logging completeness (minor): marriage reads log only spouse1;
   dissolution writes log no access at all; `setMedical` audits `INSERT` even
   when updating an existing row.
6. Dissolutions expose no amendment path though the schema supports
   `SUPERSEDES_ID` — acceptable scope cut; note it in the contract deviations.
7. Open items unchanged: Stage 3a #1 (person-satellite bitemporal decision —
   ADR-0011), search access-logging, `/me`, security-event listener,
   `verifyChain` head check, SECURITY.md caveats, ruff nit.

### ADR / ARCHITECTURE impact
